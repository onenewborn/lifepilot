# LifePilot 饭点定了

LifePilot 是一个把“今天吃什么”做成可协作 AI 体验的小程序产品。它不是简单的商家列表或优惠券聚合，而是让一个有记忆、有复盘能力的 AI 伙伴“小汪”陪用户完成饭点决策：理解当下场景，生成可滑动的吃饭方向，推荐真实商家与优惠，并把用户的选择过程沉淀成长期偏好。

我们的核心想法是：**吃饭推荐不应该只回答“附近有什么”，而应该逐渐理解“这个人为什么会这样选”。**

## 我们解决的不是信息不足，而是决策困难

本地生活平台已经有大量商家、评分、优惠和距离信息，用户真正卡住的地方往往不是“附近有没有吃的”，而是：

```text
我现在饿了，但说不清想吃什么
我不想再看冷冰冰的列表
我不想把选择完全交给 AI
我希望系统越来越懂我，但又不想被黑盒画像
```

LifePilot 把“今天吃什么”从搜索问题改造成一个可交互、可记忆、可复盘的偏好学习过程。用户每一次保留、划掉、停留、确认和复盘，都不只是完成这顿饭的选择，也是在帮助小汪理解下一次应该如何推荐。

## 产品新意

**1. 从搜索推荐变成陪伴式决策**

传统点餐推荐通常从关键词、距离、评分开始。LifePilot 从人的状态开始：一个人吃还是多人聚餐、预算、距离、口味、想省事还是想奖励自己。小汪会先把模糊需求整理成几个“饭点方向”，用户像刷卡一样保留或划掉，系统再进入具体商家和套餐。

**2. 我们为什么不只做自然语言 AI 助手**

很多 AI 本地生活助手把体验收束在“用户问一句，AI 回一段”。这在信息查询上有效，但在“今天吃什么”这件事上并不够。吃饭不是一个可以完全外包给模型的判断，它混合了饥饿程度、即时情绪、预算、距离、口味、身体状态、对新鲜感的期待，以及很多用户自己也说不清的偏好。

如果 AI 只用自然语言直接给答案，用户会被迫在“相信 AI”和“重新提问”之间选择。LifePilot 的判断是：**AI 应该帮助用户缩小问题空间，但最终的决策权必须交还给用户。**所以我们把推荐拆成一连串可感知、可比较、可反馈的卡片，让用户在保留、跳过、确认、复盘的过程中逐步表达自己。模型不是替用户做决定，而是在用户做决定时学习用户。

对比普通 AI 问答式本地生活助手，LifePilot 的路径更像一个持续协作的选择系统：

| 体验 | 普通 AI 本地生活助手 | LifePilot |
| --- | --- | --- |
| 用户输入 | 用户问一句“附近有什么推荐” | 用户可以自然语言表达，也可以直接进入滑卡 |
| AI 输出 | 直接给几家店或一段解释 | 先生成饭点方向，再进入商家/优惠滑卡 |
| 决策权 | 用户要么接受答案，要么重新追问 | 用户在每张卡上低成本表达保留、放弃和确认 |
| 个性化 | 通常依赖当轮 prompt 或历史聊天 | 会话行为、滑卡轨迹、复盘结果和确认记忆共同参与 |
| 透明度 | 用户很难知道 AI 为什么懂自己 | 汪记本展示今日小结、画像、待确认记忆 |
| 下一次推荐 | 多数仍是重新问答 | 本次选择会沉淀为下一次推荐的结构化信号 |

**3. 为什么一定要做滑卡**

滑卡不是一个为了好看的交互，而是 LifePilot 的核心产品机制。它解决了三个问题：

- **把决策权交给用户**：用户不需要接受 AI 的单点答案，而是在方向卡、商家卡、套餐卡之间逐步筛选。每一次保留或划掉，都是一次低成本表达。
- **把偏好学习嵌入自然行为**：用户未必愿意认真填写“口味偏好表”，但会在真实选择里暴露偏好。喜欢热乎下饭、抗拒排队、偏好套餐、今天想吃辣，这些都可以从滑卡行为、停留、选择和餐后反馈中被提取出来。
- **把工具变成内容体验**：传统本地生活产品常常是冷冰冰的信息流，用户像在价格、评分和距离里做筛选。LifePilot 希望把“满足基础欲望”的过程变成一个有视听感受、有当下情绪、有陪伴感的内容体验。用户不是在表格里找饭，而是在一张张具体的食物、场景和 AI 推荐语里感受“我现在到底想吃什么”。

这也是为什么我们不把商户内容简单做成列表。用户来到 LifePilot 时，本身就是带着“我饿了，但我不知道吃什么”的明确问题来找答案；这和短视频平台里漫无目的地刷快乐不一样。商户的视频、图片和套餐内容在这里不是打断用户的广告，而是用户寻找答案时需要被感知的候选项。每张商户卡下面都有小汪基于当前需求写出的推荐语，用户看到的不是“商户在宣传自己”，而是“有个 AI 助手正在帮我解释为什么这家店适合现在的我”。

因此，滑卡体验同时承担了推荐、表达、内容消费和记忆采集四个角色。它让产品不只是一个问答工具，而是一个用户愿意停留、愿意继续探索、也愿意反复使用的饭点内容场。

这也是一个内容产品判断：用户在 LifePilot 里看到商户视频、图片和套餐时，并不是像刷短视频一样漫无目的地等平台投喂快乐，而是带着“我现在饿了，但我不知道吃什么”的明确问题寻找答案。商户内容在这里不再只是广告素材，而是被 AI 翻译成“为什么这家店适合现在的我”的决策内容。小汪的推荐语把商家自我宣传转成用户当下语境里的解释，让用户在视听感受中确认自己的食欲和情绪，而不是在价格、评分、距离组成的表格里做机械筛选。

**4. 推荐过程本身会成为记忆**

用户不一定每次都明确说“我喜欢什么”。LifePilot 会观察用户在挑饭时的犹豫、保留、跳过、确认和餐后反馈，把这些行为转化为短期观察和可确认的长期偏好。小汪日记本会把当天的选择过程写成复盘，用户可以决定哪些偏好值得被记住。

我们的记忆不是简单地把聊天记录塞进 prompt，而是分成几层：

- **会话记忆**：记录一次饭点决策中的入口需求、方向选择、商家滑卡、套餐选择和最终结果。
- **短期观察**：从今天的行为里总结“用户今天似乎在意什么”，例如预算、距离、热乎感、辣度、是否想省事。
- **待确认记忆**：系统不会擅自把所有观察写成长期偏好，而是生成候选记忆，让用户在日记本里确认、编辑或拒绝。
- **长期偏好**：只有被确认的内容才会进入更稳定的用户画像，并在下一次推荐中作为强信号使用。

**5. 推荐排序不是黑盒，而是可解释的特征系统**

LifePilot 的推荐不是简单把全部商家打分后取 Top10。后端会先处理硬约束，再对剩余候选做可解释排序：

```text
明确想吃川菜 -> 先过滤非川菜相关 offer
明确人均 50 以内 -> 先过滤超预算 offer
明确一个人吃 -> 先过滤不适合 solo 的 offer
明确不要辣 -> 先过滤中辣及以上 offer
放弃某方向 -> 过滤纯属于该方向且未被保留方向覆盖的 offer
```

过滤后的候选再进入 feature-based scoring。每张商家卡都可以带上结构化评分来源：

```json
{
  "source": "current_need",
  "key": "cuisine.match",
  "score": 18,
  "reason": "命中用户当前想吃的川菜"
}
```

第一版权重被拆成清晰来源：

```text
current_need          当前需求，例如菜系、预算、距离、辣度
swipe                 用户刚刚保留或放弃的方向
memory                长期偏好和画像生成的 recommendation signals
merchant_feedback     商户或 offer 历史反馈
default_tiebreaker    距离、价格、出餐速度等默认排序信号
```

这让 LifePilot 能解释“为什么第一名比第十名更值得推荐”，也让小汪的商户优缺点文案不只是泛泛地说“我推荐你吃这个”，而是能引用排序中的关键加分点和风险点。

**6. 小汪日记本把个性化做成透明体验**

日记本不是后台日志，而是面向用户的记忆界面。它会展示今日小结、本周小结、食物选择画像、待确认记忆和已经记住的偏好。用户能看到 AI 为什么越来越懂自己，也能决定哪些内容进入长期记忆。

小汪日记本承担两个关键职责：

- **让用户信任个性化**：用户能看到“小汪是根据哪些选择理解我的”，而不是突然被一个黑盒模型贴标签。
- **让记忆持续变好**：用户可以把系统总结得不准的地方改掉，把重要偏好确认下来，把不想被记住的东西拒绝掉。这样记忆不是一次性生成，而是在使用中被校正。

**7. Memory Intelligence 不是聊天记录堆 prompt**

LifePilot 借鉴了 Claude Code 中 dreaming 机制的设计思想：AI 不只在用户发消息时即时反应，也可以在任务结束后对过程做离线整理，把零散行为转成下一次可用的上下文。但在工程命名和产品架构上，我们把这套能力统一收敛为 **Memory Intelligence**。

Memory Intelligence 的目标不是写一段漂亮总结，而是把“今天用户如何做决定”转化为“明天如何更懂用户”的结构化资产：

```text
用户行为与对话
-> memory observations
-> weak hypotheses
-> memory candidates
-> 用户确认
-> confirmed preferences
-> recommendation signals
-> 下一次推荐排序和小汪解释
```

因此，长期记忆不会被粗暴地塞进 prompt，也不会被系统偷偷写死。Memory Intelligence 会先把观察沉淀为候选记忆或画像线索，产品后端负责校验和落库，用户确认后才会进入长期偏好。快速滑卡链路不实时翻完整历史，而是读取已经加工好的 `recommendation_signals`；问小汪、汪记本和手动日/周复盘则可以读取更丰富的记忆上下文。

**8. 复盘不是总结，而是下一轮推荐的输入**

一天中用户的挑饭行为会被整理成 day context：今天发起了哪些饭点会话、保留了哪些方向、在哪些商家前犹豫、有没有完成闭环、哪些偏好可能值得进入长期记忆。Memory Intelligence 会基于这些材料生成今日小结、待确认记忆、食物选择画像和下一次互动建议。

这些结果会回到产品后端，成为下一次推荐的可执行输入。也就是说，汪记本里的“今日小结”不是孤立的日记，而是个性化推荐系统的可见界面。

**9. AI 不是一个接口，而是一个协作 workspace**

项目把前端、后端和 OpenClaw agent workspace 放在同一个交付仓库中。OpenClaw 不是外置脚本，而是产品体验的一部分：它负责小汪的人设、技能、记忆智能、饭点复盘和后台任务。产品后端提供稳定 API，agent workspace 通过这些 API 读写上下文，形成“产品 runtime + agent runtime”的双运行时架构。

最终，LifePilot 想形成的不是“用户问，AI 答”的线性关系，而是一个持续学习的闭环：

```text
当下情绪与需求 -> 饭点方向滑卡 -> 商家/优惠滑卡 -> 用户选择证据
-> 小汪复盘 -> 记忆候选 -> 用户确认 -> 长期偏好 -> 下一次推荐更准确
```

## 当前能力

- 小程序端“饭点定了”：问小汪、挑饭、滑卡、日记本三段主流程。
- 后端 API：饭点 session、商家/套餐推荐、记忆候选、长期偏好、汪记本和 Memory Intelligence job。
- 商家数据：云端当前数据包含 20+ 商家与多类套餐/优惠，支持按场景进入推荐。
- 记忆系统：产品后端记忆账本 + Memory Intelligence 分析链路。
- OpenClaw workspace：包含小汪规则、skills、记忆智能、饭点 offer flow 和后台协作脚本。

## 技术架构

```text
apps/lifepilot-miniprogram/     微信小程序前端
server/                         Node.js 后端 API
data/                           产品数据、商家、套餐、规则与 schema
docs/                           产品合同、架构说明和交付文档
openclaw-workspace/             云端 OpenClaw agent workspace 干净快照
```

运行时边界：

- 产品 runtime 负责小程序、后端 API、饭点 session、推荐数据、记忆 CRUD 和资产合同。
- Agent runtime 负责小汪人格、OpenClaw skills、记忆复盘、后台任务和自然语言协作。
- OpenClaw 通过后端 API 读取和提交产品上下文，不直接修改产品数据库运行态。

## 交付重点

LifePilot 的创新点不在于“又做了一个美食推荐”，而在于把 AI 推荐拆成了一个能被用户参与、被系统记住、被 agent 复盘的完整闭环：

```text
模糊需求 -> 饭点方向 -> 商家/优惠滑卡 -> 选择证据 -> 小汪日记 -> 长期偏好 -> 下一次更懂你
```

这让每一次吃饭选择都成为下一次个性化的燃料，也让 AI 从一次性问答变成持续协作的生活伙伴。
