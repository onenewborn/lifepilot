# apps

这个目录存放 LifePilot 的用户端应用。当前主线只有微信小程序 `lifepilot-miniprogram`，它承载“问小汪、挑饭、汪记本”三个入口，是评委和真实用户最直接接触到产品价值的地方。

LifePilot 的优势不在于把后端接口简单包成页面，而是把 AI 推荐做成可参与的生活决策体验：用户可以先和小汪对话，再进入滑卡流程，最后在汪记本里看到系统如何理解自己的选择。前端的职责是让这条闭环变得轻、顺、可感知。

## 当前内容

- `lifepilot-miniprogram/`：微信小程序主工程，当前唯一正式应用。

## 支持的产品服务

`apps/` 这一层支撑的是 LifePilot 的用户触点，而不是后台逻辑。它回答的问题是：用户如何把“我不知道吃什么”变成一系列可表达、可比较、可确认的动作。

当前小程序支持：

- **问小汪**：用户用自然语言表达“想吃川菜”“直接帮我选”“这家怎么样”。前端负责聊天、loading、skill 卡和历史会话展示。
- **挑饭滑卡**：用户通过方向卡和商户卡做低成本反馈。前端负责手势、媒体展示、卡片切换和最终确认体验。
- **汪记本**：用户查看今日小结、本周小结、食物选择画像、待确认记忆和已确认偏好。前端负责让个性化过程透明可控。
- **媒体内容体验**：商户图片、视频、套餐和 AI 推荐语共同构成“内容化本地生活推荐”，不是普通信息流列表。

## 创新点在前端如何体现

- **不是列表，而是决策过程**：用户不会直接看到一页商家列表，而是先和小汪交互，再经过方向卡和商户卡逐步收束。
- **不是让 AI 直接替用户决定**：前端始终保留用户的保留、划掉、确认和拒绝动作。
- **不是黑盒个性化**：汪记本把系统理解用户的过程展示出来，用户可以确认或拒绝记忆。
- **商户内容不是广告流**：视频和图片被放在“用户正在找答案”的语境中，并由小汪解释为什么适合当下需求。

## 设计边界

- 应用端只负责展示、交互和轻量状态恢复。
- 饭点 session、推荐排序、记忆账本、Memory Intelligence 结果都以后端为准。
- 新增应用时应保持和主产品 runtime 的边界清晰，不要把后端规则或 OpenClaw workspace 逻辑复制到前端。
